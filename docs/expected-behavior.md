# Expected behaviour

This is the implementation reference for Yuriful's current canvas and storage. Read the sections affected by a change before implementing or reviewing it. Settled rules are constraints; named open questions remain open. For how to use the app and its known limits, see [README.md](../README.md). For product direction and working rules, see [AGENTS.md](../AGENTS.md).

## Captions and frame navigation

- Interaction feedback marks the frames that may gain or lose items and highlights items carried by a frame. During a drag, moving toward the canvas edge pans the view and keeps the grabbed item under the pointer. Disabling interaction feedback turns off edge panning. Caption snapping has its own switch.
- Caption snapping defaults to on when its preference is absent. Canvas options live in browser storage scoped to the profile and site origin, separate from the board. Loading preferences leaves the saved value alone. Earlier builds saved both options whenever either changed, so every stored `captionSnap: false` is retained.
- An image may have one attached caption. An attached caption shares the image's frame ownership and follows the image when it moves. Legacy captions start with their saved coordinates and use their existing edge alignment when a placement changes.
- With caption snapping enabled, dragging upright text near an available image edge previews its landing. The caption stores its center as a fraction of the edge length, including the endpoints, and uses that fraction when the image resizes. The displayed upright bounds of a rotated or cropped image determine its edges. Ctrl or Cmd at release suppresses the snap. Interrupted gestures restore the previous scene.
- An attached caption may have a solid background color. An absent color draws no box. Attachment edits, background changes and transforms use the normal undo and save lifecycle.
- A frame jump moves only the viewport. Several jumps share the original return point. A no-op jump leaves the return point and save state alone. Returning restores the original zoom and pan exactly. A changed manual view or canvas resize clears the return point.
- Frame tour uses a detached scene captured at entry, with selected frames taking precedence over visible frames. Previous, Next and Esc operate inside the tour. Entering or leaving a tour creates no board edit, selection change, viewport change, history entry or save.

## Editor and gesture invariants

- What is drawn: frame paper, images and text are elements of the scene layer (`sceneLayer.ts`, kept in step by `domScene.ts`), under the Fabric canvas, in exactly the board's stacking order, so images and text interleave freely. Every object on the canvas is a transparent proxy: it paints nothing and takes selection, handles, hit testing and transforms. The canvas paints frame outlines, frame labels, selection chrome, crop mode's overlay and the draft rectangle above all content. The layer follows each proxy's matrix in the same frame as the canvas. Only one text is live at a time (the edited one); every other card is static, so selected text cannot be dragged from one text into another. Dragging within the edited text, and cut and paste between texts, work.
- A pointer gesture is settled (selection re-formed, scale folded, ownership decided, history recorded) in one microtask queued from Fabric's callback, after Fabric's own mouse-up handling has returned. Removing an object is deferred the same way. One thing does run inside a callback: a moved frame's followers are placed during `object:moving`.
- A text being edited changes only through its edit session (`textSession.ts`): every change is one transaction of its `dispatch`, refused once the edit has ended, while the board is read-only or a gesture is unsettled, or when another edit has started. After each change the canonical record content goes to the card, before the typing save is scheduled: each line keeps the level it had before the change (`textAfterEdit` in `richText.ts`), marks and fonts come from the document, and the proxy is sized from the card at once. A typing shortcut converts in the same input (see below), so no save sees a marker typed but not converted. Leaving the edit (`finishEditing`, by every route: Esc, Tab outside a list item, a press outside the edited text, a tool, panel or layer-list command, the text ceasing to be selected) puts the static card back, sizes the proxy, discards a blank text, decides a new text's owner once more and commits. A press outside the edited text ends the edit and is then passed to Fabric as the same press, so it selects, drags, marquees or starts a draft as it would have; a frame's label or outline, and an unlocked object in front of the text, count as outside.
- Pasted text never brings its own size, colour, font or heading level. Plain text takes the formatting of the place it is pasted (and of the start of the selection it replaces), with the three kept quirks listed in the README. HTML (text copied in Yuriful, or from a web page) keeps its own bold, italic, underline and strikethrough, takes the font of the place it is pasted, and arrives as plain paragraphs (a heading arrives bold at normal size). HTML is parsed in an inert document: pasting never loads anything. A pending mark or font applies to text pasted at the caret.
- While an IME composition is open the browser owns the text: the session changes nothing until it ends, then sets marks and the canonical form on the composed text as part of the composition's undo step. A composition never starts over a selection: the selection is deleted first, as an ordinary edit carrying the composition's own `composition` id in a text with blocks, so the deletion and what the composition puts in are one in-edit undo step (how the deletion joins what came before it is ProseMirror's usual grouping; a text without blocks keeps that grouping exactly, untagged); a deletion refused because its result could not be stored refuses the composition too (`imeRefused`: taken back when it ends, never in a record before). A command that would change the text does nothing while a composition is open or ending; alignment and colour still apply. Composed text takes the formatting of the caret, or of the first selected character.
- A save never sees an unfinished gesture or an open crop: while one exists, the saved scene is the one from before it. Title and viewport are always live.
- Esc, a window blur, or the board going read-only cancels an unfinished drag, resize, scale, rotation, frame draft or text draft and restores the board from before it, with no history entry and no save. A press that moves nothing leaves no trace.
- While a gesture is unsettled only Esc and the zoom keys respond; every editing command and shortcut is ignored (an image import waits and is added afterwards as its own undo step). Wheel panning and zooming keep working (a wheel movement during a gesture always pans), and the title stays editable.
- Only the primary mouse button edits. Presses of other buttons never reach Fabric, and a non-primary release during a primary drag is kept from it; the middle button pans. A primary release over a disabled control (Chromium sends only `pointerup` there) is passed on as a `mouseup` from the control's enabled parent, so a drag released over a greyed-out panel button ends there and is kept; the control does not act and nothing is clicked. A mouse press on a disabled control has its `pointerdown` default prevented, so it never takes the keyboard from the text being edited (a touch or pen press still does: a known limit).
- Undo and redo restore whole scenes, including frames and ownership. A commit that changes nothing records nothing and saves nothing.
- While a text is edited, Undo and Redo, by key or by the toolbar buttons, step through that edit's own history (typing, deleting, pasting, marks, headings, fonts, typing shortcuts and their Backspace revert) and keep the edit open; `EditorState.canUndo` and `canRedo` then follow that history. Whole-box settings changed during the edit (font size, alignment, colour) are record fields, not steps of it. Leaving the edit records it as one board history step, with one exception kept from the shipped canvas: a font size change during an edit records the edit so far, at the new size, as a board step of its own while the edit stays open, so what follows it becomes a second step when the edit ends (replace an existing text's words with `First`, set the size from 24 to 36, type ` second`, Esc: the first board Undo gives `First` at 36, the second the original text at 24). The exception does not apply to an attached caption (the size change is saved and the caption kept against its image, and the whole edit stays one step: the first Undo after leaving gives back the caption as it was before the edit) nor while the edited text is blank (nothing is recorded until the edit ends).
- After `dispose()` the autosaver never saves again: nothing is scheduled, a save already in flight finishes without rescheduling or reporting, and `Editor.getDoc` refuses to describe the board (its canvas is being cleared).

- The Text tool's drag is a draft gesture like the Frame tool's (`Gesture.draft` with `tool: 'text'`, drawn through `canvas.draft`). It starts on a primary press on empty canvas or a frame's interior with the Text tool chosen, the hand out of effect, the board editable and no gesture in progress. Release settles in the usual microtask. Staged image imports go first because adding one ends the edit and would discard a new blank text. `addTextAt`/`createObject` then takes the drag's smaller x and y, width and minimum height if it meets the click slop in screen pixels and is at least two font sizes wide in scene units (`MIN_TEXT_DRAG_EMS`). Clicks and smaller drags get the default box (ten font sizes wide) at the press point. A `mouse:up` without a press creates nothing.
- A drawn text's actual height is its text height or stored `minHeight`, whichever is taller, unless it has a fixed `height`, which is its height whatever its text; a drawn `minHeight` is then kept but counts for nothing until Auto height. Text starts at the top. Drawn boxes wrap at spaces and split overlong tokens at grapheme boundaries. The widest individual grapheme may raise the usable minimum width. Click-created boxes and earlier records wrap only between words (a token the browser could break inside, such as `state-of-the-art` or a CJK run, is kept whole) and widen to their longest word, keeping their alignment edge in place; a box never narrows by itself. Side handles change width. Corner scaling also scales and folds the drawn minimum height along with width and font size.
- **Fixed height (Slice 4).** The bottom handle (`mb`, action `resizeHeight`) sets `height`, held to at least `minFixedHeight` (1.5 font sizes, rounded); the top edge stays, the width and wrap never change, and it is a resize for ownership. The body scrolls (`overflow-y: auto`, native scrollbar hidden: no width is ever taken). Double-clicking `mb` or Auto height (`setTextAutoHeight`) clears `height`: one undo step on a selected box, part of the edit's step while edited (saved at once), ownership unchanged, a caption placed again against its image. Corner scaling folds `height` with `fontSize` and `width` once; side handles leave it alone. A fixed-height text's proxy is `width × height`: ownership, snapping, alignment, captions, hit testing, duplicate and previews use that box. A caption keeps its image through a bottom-handle drag (unlike a width change, which detaches it) and is placed again against it when the drag settles.
- **Scroll position is view state.** Kept per card while the board is open (through edits, undo and redo of other things, culling), clamped when the text gets shorter, dropped when `height` changes or goes, never stored, compared or in history, never dirty, never changes selection or ends an edit. A reload and every frame preview start a card at the top.
- **Wheel ownership (Owner Decision 9, Option B).** Plain wheel events less than `WHEEL_LATCH_MS` (180) apart are one gesture; the first picks the owner and the rest follow it. The owner is a fixed-height card when the board is free (loaded; no gesture, pan, draft or crop; neither a chosen hand tool nor Space), Shift is not held and the wheel is mostly vertical, no frame label or outline is under the pointer, the card is the front-most object whose box holds the pointer (locked objects count), and it has room to scroll that way. A card owner scrolls by `deltaY × unit / zoom` and stops at its end; otherwise the board pans as before. Ctrl/Cmd+wheel zooms and ends the gesture. Read-only boards follow the same rule and write nothing; while loading the wheel is ignored.
- **Cues.** `fade-top` and `fade-bottom` on the card mask its body over 20 px with no layout shift; a fixed card's caption background and edit outline sit on the card, so neither fades. The 6 px thumb shows while the text scrolls, fades 800 ms after, and can be dragged only while the text is edited. The caret is kept 20 px clear of the fades.
- Nothing is editable or saved before the stored board has loaded. A board that cannot be fully restored, or that another tab has changed, is read-only: no selection, no edits, no writes, no pruning; pan and zoom still work.
- A blank text is never part of the scene: it is not saved, not in history, and is discarded when its edit ends, whatever formatting it has. A text is blank when it has no non-whitespace character **and** no divider **and** no ticked checkbox (`isBlankTextDoc`, owner decision 4): only `# `, `- `, `> ` or `- [ ] ` typed is blank, only a divider or a ticked box is content. An existing text emptied to an empty list is left out of the scene while edited and discarded when the edit ends, as one undo step.
- A text's formatting on the canvas is always its canonical record: what a save stores is what the canvas shows. The card is drawn from the record (`textSchema.ts`), and while a text is edited its session is the live source of truth, reporting the canonical content after every change. A text with no rich field is stored in the compact form (`text`, `spans`, `headings`) exactly as earlier builds stored it; a text that uses any block other than top-level paragraphs and headings, or inline code, is stored as `blocks`, and goes back to the compact form when it no longer does.
- A heading is a property of a line (a heading block in the text engine's document). After a text change a line's level is carried over from the levels before the change and how the text changed (`textAfterEdit` and `headingsAfterEdit` in `richText.ts`, the single authority), never derived from character sizes; the bold of a heading is never stored as a mark. A formatting command while editing is one transaction of the session (`textRules.ts`); on a selected box it is a pure whole-box function (`textRules.ts`) ending in the canonical compact record; scale folding and `setFontSize` change the base size, and headings follow at their ratio. Either way the box's alignment edge stays where it is, and the text, the caret and the selected range are never touched.
- Formatting commands act on the one selected text, behind the `editable && !busy` guard. While editing, marks, font and heading act on the selected range (a line touched only by a range that ends at its start is not counted). Alignment and colour act on the whole box. The change is saved as it happens and is part of the one undo step recorded when the edit ends (leaving an edit always commits). On a box outside editing, all commands act on the whole box as their own undo step, coalesced per kind and text like the font size. A whole-box font change sets the base font and clears the span font overrides. A whole-box heading applies to every line but an empty last one (`lastBoxLine` for both the panel and the command). Body text also clears an empty last line. A command that changes nothing records and saves nothing. A command on a blank text being typed into saves nothing and records no removal.
- Marks and a font chosen with only a caret are pending. The session keeps them for that text, shows them as the next character's state and gives them to the characters typed, composed or pasted at the caret. It drops them on a caret move other than typing or composition, when the edit ends and when records are applied. A heading line is always bold. A pending bold, and only bold, is dropped whenever the caret's line is or becomes a heading, after a heading command or text change (`typedMarks` and `canonicalGuard` in `src/editor/textRules.ts`). A Backspace revert of a shortcut restores all pre-shortcut pending formatting. Bold changes only the normal lines in a mixed range.
- Typing shortcuts (`# `, `## `, `### ` at the start of a line; a closing `**` or `*`) fire only for one character typed at the caret with nothing replaced: the character is the one `typedCharacter` saw on its keydown, the text is the edited one, the board is editable, no gesture is unsettled and no IME composition is in progress (ProseMirror's own input rules and paste rules are off). Pasted, dropped, composed and loaded markers stay literal. The matcher (`matchShortcut` in `src/editor/textRules.ts`) is given only the caret's line; its literal cases are pinned by tests. A conversion is two steps of the edit's history: the typed character, then the conversion. After bold or italic fires, what is typed next is plain through a pending "off". Backspace straight afterwards (no modifier, not repeated, from the edited text, not composing) restores the exact pre-conversion text, formatting, caret and pending marks, as a step of the edit's history; Ctrl/Cmd+Z straight afterwards undoes only the conversion. The Backspace offer is dropped by the next text change, any caret or selection move, an in-edit undo or redo, any formatting command or font size change, the end of the edit and `applyRecords`. A conversion never changes ownership and is part of the edit's one board undo step.
- Block shortcuts, typed under the same conditions (one character a key typed, at the caret, nothing replaced, never composed, pasted, dropped or loaded; `typedCharacter` now also reports `-` and a backtick): at the start of a plain paragraph (top level or in a quote) `- ` makes a bullet list, `1. ` (a whole number from 1 to 999,999,999) a numbered list starting at it, `[] ` or `[ ] ` an unticked checklist item, `> ` a quote, a line that is exactly `---` a divider followed by an empty paragraph, and ```` ``` ```` a code block holding the rest of the line; at the start of the first paragraph of a bullet list item, `[ ] `, `[] ` or `[x] ` makes that item alone a checklist item (owner decision: the two-stage `- [ ] `). Inside a line, a closing backtick makes inline code by the italic rule (`matchCodeShortcut`). `* ` never makes a list (owner decision 7). Nothing fires in a code block, for a character typed inside inline code, or when any marker character is inline code. Each is two steps of the edit's history with the same Backspace revert. A list typed beside a list of its kind joins it (a numbered one only when its number follows on); a quote joins a quote beside it.
- Lines are textblocks (paragraphs, headings, code blocks) wherever they sit: offsets, the heading rule (`headingsAfterEdit`, a code block's own line breaks stood in for), the canonical runs and the controls' line readouts all work per textblock, so a text without blocks behaves exactly as before.
- Tab and Shift+Tab in a list or checklist item indent and outdent it (`sinkListItem`, `liftListItem`; out of the list from the top level) and keep the edit open; Tab on an item that cannot go deeper (the first of its list) does nothing and keeps the edit open (owner decision 8). Elsewhere Tab leaves the edit.
- Enter in a list item makes a new item (unticked in a checklist); on an empty last line of an item it moves the item out one level. Enter on an empty line straight inside a quote takes it out. Enter in a code block is a line break, wherever the code block sits (in a list item too: the code rule comes first); on its empty last line it leaves the block. Enter over a selection that reaches into a list item from another line deletes the selection, then acts at the caret it leaves. Backspace at the start of the first line of an item lifts it, of a code block turns it into paragraphs, of the first line of a quote lifts it out, and just after a divider deletes the divider; Delete at the end of a line just before a divider deletes it.
- A checkbox is toggled by a press on it while its text is edited, as one transaction of the session (saved like typing); nowhere else. Each toggle, and each block command (list, quote, code block, divider, indent, outdent), is an in-edit undo step of its own (`closeHistory` before and after it), never merged with typing or another command beside it.
- Block commands (`toggleBlock`): while editing, on the lines the selection touches (none when only a divider is selected, `linesOfState`: the list, quote and code-block commands then change nothing and read off); on a selected box, on every line of the text, empty ones and the last included (`toggleBlockKind` with `wholeBox`, through `boxCommandContent`, what `boxBlocks` reads), as its own coalesced undo step. The rule of the list, quote and code-block commands (`toggleBlockKind`): after one, every line concerned has that block (turned on) or none of them has it (turned off: every one of them was already in it), so the readout reads on or off, never mixed; and every line outside the selection keeps exactly the blocks it had (the kinds of list, quote and code block around it, its ticked state, the number it is painted with, its text, marks and fonts); selected lines keep their text, marks and fonts (except what a code block cannot hold) and, staying checklist items, their ticks; a change refused for a stored bound changes nothing. It is met by reading the document as a flat sequence of leaves (lines and dividers) with the blocks around each, changing only the selected lines' blocks, and building the document again, in one pass with no cap on the number of blocks. A line that leaves an item an unselected line also belongs to leaves the item behind for it (the item may then start with a list). On, a selected line in a list of another kind gets a list of this kind in its place, and one in no list gets one around it (a new checklist item unticked). Selected lines next to each other at the same level that end up in the same kind of list are one list (next to each other in the same parent: only what is nested in the earlier line's item may come between, so a nested item never splits its parent's list), an existing list of that kind that one of them is in included (it joins with all of its items); a list none of whose lines is selected is never joined. A divider goes with the lines a list or quote command acts on (`carryDividers`, one pass) when its container (for a list command its list item; for Quote its innermost list item or quote) holds no line the command does not act on, and it lies inside the selected range (after the line the selection starts in, before the line its end is in, a line it ends at the start of included) or its container holds lines; a list command moves a divider only with its item. A numbered item keeps the number it was painted with when its first line (a divider at its start does not count) is not acted on. Every numbered item whose first line is not selected keeps the number it was painted with: a part of a list starts at its first item's number, and a list is cut where counting on would paint such an item with another number (`rebuild`); a list that would need a start that cannot be stored (`isListStart`) refuses the command. Other items count on from the item before. The command replaces only the part of the document that changes (`replaceChanged`), and it is marked as keeping the text (`META.keepsText`): a text stored with "\r\n" line breaks keeps them through a block command, and through an in-edit undo or redo that gives back the same characters (`EditSession.keepsText`), so Undo after a block command restores the stored record byte for byte. Code joins neighbouring selected lines into one code block; off, each code line becomes a paragraph. A seeded randomised test (`textBlocksRule.test.ts`) pins the rule, in an edit, with only a divider selected and on a selected box through the whole-box command, with one undo giving back the stored record exactly. Marks (`toggleRangeMark`) and fonts never apply to a code block's text (it is always Mono): the panel disables Bold, Italic, Underline, Strikethrough, Inline code and the fonts when every line concerned is code, their keys do nothing, and no font is set pending in a code block. A divider goes in at the caret (never on a box outside an edit, nor in a code block). Inline code follows the mark rules (`toggleRangeMark`; pending with only a caret). None changes ownership.
- In a text with blocks, typing, pasting, Enter, Backspace, Delete and the deletion that starts an IME composition, over a selection, leave the text before the selection, then what came in, then the text after it, a record that can be stored, the line the two ends became the line the selection started on (its kind, a code block or not, a heading's level following the line-level rule; the blocks around it with a checklist item's tick and a numbered item's painted number), every line after the selection with the blocks, tick and painted number it had (a list cut in two gives the part after the start that keeps them, as the block commands do), and a collapsed caret after what came in, whatever blocks the selection starts in, ends in and crosses (`settleReplacement`, applied in `EditSession.dispatch`; Enter over a selection across lines deletes it so and then does what Enter does at the caret, `enterOverItems`). With a divider selected on its own (a node selection, `replaceDivider`), Backspace or Delete removes it and leaves a caret where it was (the start of the line after it, or the end of the one before), and typing, a paste, Enter (`enterOverDivider`) and the start of a composition put a line in its place holding the input (Enter and a composition: an empty line), caret after it. What the page shows after any input is what the session holds: a refused input leaves page, session and selection as they were, a refused composition included (taken back when it ends). In a text without blocks (paragraphs and headings, no inline code) the step does nothing: the transaction, its selection and its history are ProseMirror's and the earlier canvas's rules'. When no storable result can be made, the input is refused whole: record and selection stay as they were. ProseMirror's own replacement is kept when it does all that; across blocks that cannot hold each other's content (a code block and a line with marks, a heading and a code block's line breaks) it is made again: the selection deleted across its lines (`deleteAcrossLines`: the two ends become one line of the first end's kind, a code block's later lines stay a code block, lines in the second end's item after it stay with their numbers), then the input at the caret. A seeded randomised test in `textBlocksRule.test.ts` pins the rule for every input.
- Nothing over a bound is written: the session refuses (`filterTransaction`) any change whose result would be stored as `blocks` and exceed depth 6, 10,000 nodes or 500,000 characters, paste included; a typing shortcut it refuses leaves the typed character as ordinary typing (no Backspace revert). While an IME composition is open the filter stands aside; if the composed text took the text over a bound, the follow-up straight after `compositionend` takes back exactly what that composition changed and nothing else: the session goes back to the state, history included, it had just before the composition changed anything (`imeStart`, taken at `compositionstart` before a selection is deleted), so the text and selection it replaced come back, typing before it stays, and it is not on the redo side. In-edit undo groups compositions as ProseMirror's history groups any change (a composition and a change next to it within 500 ms share a step); the refusal does not depend on that grouping and does not change it. The refusal also happens when the composition ends any other way (the edit finishing, the board going read-only). And the one place the session hands its content out (`content()`: typing saves, the idle card, the end of the edit) never holds such a composition: while one has the text over a bound, open or not yet followed up, the content is the one from `imeStart`. A whole-box command outside an edit (`formatBox`) is refused the same way: nothing changes, records or saves. A numbered list's start is a whole number from 1 to 999,999,999 (`isListStart`, `MAX_LIST_START`), for the shortcut, the schema and storage alike (any other stored start is read as 1), so every number a list reaches is below what browsers paint (2^31 - 1).
- A paste into a code block is plain text (the clipboard's, or the words of its HTML); a paste with no text at all changes nothing. The earlier canvas's paste styling (`plainPasteContent`) applies only between documents that are compact before and after the change.
- A frame preview shows a numbered list's long number where the board shows it, past the text's left edge (`numberOverhang` widens the card's bleed), and a card whose number reaches into a frame from outside it is drawn in that frame's preview (`numberReach`, from the record, decides before laying the card out).
- Wrapping inside blocks keeps the two box rules: a line's floor is its widest word (widest grapheme on a drawn box) plus how far its blocks move it in (`LIST_INDENT_EM`, `QUOTE_INDENT_EM`, a code block's padding, in em of the base size, the same values as the stylesheet); a drawn box's no-wrap words are judged against the box width less that indent. A code block wraps anywhere in every box and keeps no word whole: its floor is its widest grapheme plus its padding.
- Formatting controls are buttons that never take focus (`Overlays` and `Inspector` prevent the mousedown default), so using one keeps the edit, its caret, its range and typing. Ctrl/Cmd+B, I, U while editing are claimed only from the edited text, never with Alt or Shift, never during composition; a held key's auto-repeat is claimed (default prevented) and toggles nothing, also on a selected box; on a box not being edited only when exactly one text is selected. `resolveShortcut` still returns null while a text is edited; Esc and Tab (outside a list item) leave the edit, and nothing claims a key with Alt held in it. Focusing the title or font size field, or the window losing focus, keeps the edit open.

## Frames (settled)

- A frame is a named, unrotated rectangle behind all content. It clips nothing. It is grabbed by its label or within 6 screen pixels either side of its outline; its interior is click-through. A label or outline wins over content lying on top of it.
- Ownership is stored on each object (`frameId`) and never recomputed from position. Loading restores it as stored (an owner that names no existing frame is dropped).
- **An object changes owner only through its own movement.** When content is moved, resized, rotated or created, it keeps its owner if that frame was transformed in the same gesture, or still contains its centre. Otherwise it joins the front-most frame that contains its centre and was not transformed in that gesture, or becomes loose. An owner is sticky: a frame in front that also contains the object does not take it.
- "Centre" is the centre of the object's box, including the wrapping width and actual height of text. The awkward case of a newly placed text whose box is much wider than its words remains an open design question in the README. A drawn minimum height contributes to the centre. The owner is decided again when the first edit ends, so text that grows below a frame may end up loose (see `e2e/texttool.spec.ts`).
- **Moving, resizing or drawing a frame never adopts anything.** A loose object that a frame was moved over or drawn round stays loose until the object itself is moved.
- Moving a frame together with loose objects leaves them loose. Things it already owns stay owned, with no containment test, when they are transformed together with it.
- Moving a frame carries its unselected members exactly once. A member that is itself selected moves through the selection only, never twice.
- A resized frame releases members it no longer contains; they become loose and are not handed to another frame. Deleting a frame keeps its contents, loose.
- A click without movement, selecting, reordering, renaming, typing in existing text, typing shortcuts in existing text, changing font size, formatting an existing text (marks, headings, font, alignment, colour, even when a heading makes the box taller and moves its centre out of its frame), undo, redo and loading never change ownership.
- Pressing the label of a frame that is part of the current multi-selection acts on the whole selection.

## Transforms (settled)

- **A frame resized alone changes its own shape freely and leaves its contents where they are.** It never stretches or moves them. Each side stops at 24 units (or at its own length if it was already shorter).
- Transforming contents with their frame is explicit: "Select with contents" selects a frame plus the unlocked things it owns, and that multi-selection is then moved or scaled as one.
- A multi-selection can be moved, scaled proportionally from a corner, and (if it contains no frame) rotated. There is no free-aspect stretch or skew of a group, and Shift does not unlock one. Every reachable canvas state must be representable in the stored records.
- One scale factor per proportional gesture: limits (text 6 to 400 px, a frame's smaller side at least 24 units) are computed from pre-gesture values and applied once to the whole selection, never per member, and an out-of-range member is never snapped into range. No transform is applied twice.

## Selection layout

- Align moves two or more unlocked selected items on one scene axis, using their displayed axis-aligned bounds. Left, top, right and bottom use the selection's outer edge. Center uses the midpoint of the selection's span. Distribute keeps the two outer items in place and spaces the gaps between three or more items. If there is insufficient room, that axis is disabled. Moves use the normal stored position precision.
- A moved frame carries its unselected members, including locked ones. A selected member takes only its own layout displacement. Apply the ordinary ownership rules to moved items and leave stationary items alone. One changed layout is one history step. Shape, angle, z-order and selection are preserved.

## Duplication

- Duplicate is inert before load, on a read-only board, during a canvas gesture and for a locked selection. A valid command finishes an edit before it snapshots the scene. Each copy has a fresh id and starts unlocked. Source image bytes are shared. One command, including a frame with its owned items, is one history step.
- Copy explicitly selected objects and the owned contents of selected frames exactly once, preserving relative stacking within each band and bringing the copies to its front. Remap ownership to matching copied frames; other content copies use the ordinary placement rule against existing frames. Select the counterparts of the items explicitly selected.

## Layers (settled)

- The layer list (`EditorState.layers`) is derived from the canvas and never stored. It is flat and front-most first: all content front to back, then all frames front to back. Content is never grouped under its frame, because stacking order is global and independent of ownership; an owned item only names its owner, taken from stored ownership.
- A blank text is not listed, including one emptied while it is being edited. A kept text with no characters (only a divider or a ticked checkbox) is listed as `Text`. A text's label follows typing: every change of the edited text refreshes the derived state, which marks nothing dirty and records nothing.
- A plain press goes to the front-most object under the pointer, except inside a multi-selection's box, where it goes to the selection (Alt or not). A locked object is never the target of a press (see Locking). With Alt held (`altSelectionKey`), a press goes to the selected object if it is under the pointer, even beneath other content, so that a covered object selected from the list can be dragged. It is an ordinary gesture (same settle path, ownership rules, one history step; Esc, also with Alt still held, and a window blur cancel it). Alt never changes frame hit rules: a frame's label or outline still wins over the selected object (`FrameCanvas.findTarget`), and a frame's interior stays click-through.
- Selecting from the list (`selectLayer`) changes nothing on the board: no history entry, no save, no ownership change. It ends a text edit first, like every other command, so typed text is committed as its own step. It is inert before the board has loaded, on a read-only board and while a gesture is unsettled.
- Reordering stays what `[`/`]` and `Ctrl/Cmd+[`/`]` already do: each kind moves within its own band, so frames stay behind content, and ownership never changes.
- Dragging in the list moves one unlocked row within its own band, including past a locked row. The upper and lower halves of a target row insert before and after it in the front-most-first list. Only a valid primary release at the previewed insertion changes the stack. The selection and ownership stay as they are. A changed drop finishes any text or crop edit first and records one reorder step. Esc, blur, a lost release, a read-only board or release without a valid insertion cancels the drag without committing a reorder.
- Rows must not take focus on a mouse press, or Space-to-pan and the letter shortcuts would act on the list. A row press first blurs a focused chrome field (font size, frame name, title), so that its keys do not act on the new selection; the edited text is left to `selectLayer`, which ends a text edit itself. The same holds for a row's padlock button, which also never selects its row.

## Locking (settled)

- Storage: `locked?: true` is optional on every content record and on a frame record. Absent means unlocked; `locked: false` or an explicit `undefined` is never stored. There is no version bump and no database upgrade: every wire version reads and writes it, and a lock never changes the version a board is written as: a board without frames or rich text is still written as version 1. `parseDoc` keeps it only when it is exactly `true` (anything else is dropped, not fatal). A lock change is a scene change, so it is a history step and is saved.
- A locked object or frame is never the target of a press: Fabric's `evented` and `selectable` are off, so a press, a hover, an Alt-press or a double-click falls through to whatever is beneath it (or to the empty board, where it starts a marquee or, with the Text tool, places a text). A marquee, Select all and Shift-click never take it; a locked frame's label and outline are not grabbable and its label does not start a rename. Its handles are hidden, its movement, scaling and rotation are locked and a locked text is not editable, as defence in depth. These flags are set in one function in `objects.ts`, used by creation, lock and unlock, so that unlocking restores exactly what creation set.
- A locked item is selected only from the layer list, and only alone: **a selection that contains a locked item contains nothing else.** A toggle click on a locked row acts as a plain click; a toggle click on an unlocked row while a locked item is selected replaces the selection; Shift-click on the canvas never adds to a locked selection (`FrameCanvas.handleMultiSelection`). `selectByIds` enforces the rule centrally for every selection the editor forms, including the one restored by id after undo and redo: locked items are dropped from a restored multi-selection, and a restored single locked selection is kept.
- While a locked item is selected nothing edits it: no move, resize or rotation, and delete, the four layer-order commands, font size, rename, "Select with contents" and text editing do nothing. `SelectionInfo.locked` is true exactly when the selection is one locked item, and every `layer` flag is then false.
- Commands: `setSelectionLocked` (the inspector button), `toggleLayerLock` (a row's padlock, whether or not the row is selected) and `Ctrl/Cmd+Shift+L` (unlock a single locked selection, otherwise lock the selection). Each is inert before the board has loaded, on a read-only board and while a gesture is unsettled, and ends a text edit first (typed text is its own step; a blank text is discarded). One history step when something changes, none when nothing does. Locking a multi-selection clears it; locking the single selection keeps it selected; a padlock that locks a member of a multi-selection takes just that member out; unlocking never changes the selection. Locking and unlocking never change position, size, stacking or ownership.
- A lock guards direct manipulation only. Frame relations keep their settled rules: a locked member keeps its owner and follows its frame's move as an unselected member, exactly once; "Select with contents" selects a frame plus its unlocked members (so a locked member follows a move and is not scaled); a frame whose size changed releases members it no longer contains, locked or not; deleting a frame leaves its locked members, loose; content moved into or out of a locked frame joins or leaves it by its own movement. A locked frame cannot be moved, resized, renamed, reordered or deleted.
- New things are never locked. The Frame tool draws over anything, as before; zoom-to-fit includes locked things; on a read-only board the padlocks are shown and inert.

## Image tools (settled)

- Storage: `ImageRecord.crop?: { x, y, width, height }` is the visible rectangle of the ORIGINAL image in source pixels (x/y from its top-left); absent means the whole image. Cropping is non-destructive: the stored bytes are never changed. With a crop, `left`/`top` are the top-left of the displayed (cropped) box, the displayed size is `crop.width * scaleX` by `crop.height * scaleY`, and `angle` turns that box as for any image. "Centre" for ownership is the centre of the displayed box.
- No version bump and no database upgrade: every wire version reads and writes `crop`. `parseDoc` keeps it only when it is an object of finite numbers with `x >= 0`, `y >= 0`, `width > 0`, `height > 0` (anything else is dropped and the image shown whole, not fatal). `serializeDoc` writes a fresh copy only when present; an undefined key is never stored, and a crop equal to the whole image is never stored (`toRecord` omits it). There is ONE stored-crop decision, `storedCrop` in `src/model/crop.ts`, used by the geometry (`coverBox`, so Fill and replace; `clampCrop`; closing crop mode) and by the Fabric conversion (`createObject`, `imageCropOf`/`toRecord`), and so by everything saved: the crop's EDGES are clamped to the image and rounded to 0.01 source pixels, its sides are taken from the rounded edges (so a stored crop never reaches outside the image and clamping it again changes nothing), and it is the whole image exactly when its rounded edges are the image's edges (no tolerance beyond the rounding: a crop that differs from the whole image at stored precision is never dropped). What Fill, Fit and replace compute is exactly what `createObject` then `toRecord` give back (pinned by seeded sweeps). The one value that is not on the 0.01 grid: a crop thinner than the stored step on an axis (under 0.01 source pixels, which only an absurd box shape produces) keeps its true positive side rather than collapsing to zero.
- `sceneEqual` compares nested record values structurally (plain objects and arrays by content; NaN equals NaN; absent equals `undefined`), so two snapshots of the same cropped image are equal and a changed crop is a change. `toRecord` reads the crop from the Fabric image (`cropX`, `cropY`, `width`, `height` against its natural size) and emits a fresh object every time. A stored crop that reaches outside the decoded image is clamped to it when the object is created (`clampCrop`, which is `storedCrop`, in `createObject`); if nothing is left the image is shown whole. A crop this build writes is never changed by that.
- Crop mode (`startCrop`): only for one unlocked image, on an editable board, while no gesture is unsettled; inert otherwise. Entry points are the inspector's "Crop image" button and a double-click on an unlocked image with the Select tool (deferred by a microtask, like the frame-label double-click; not when the double-click began with the press that applied a crop). Starting it switches any other tool to Select. `EditorState.cropping` says it is open.
- While cropping, the whole original is shown in place (the kept pixels do not move), the part outside the crop rectangle is dimmed, and a box with eight handles is drawn in `after:render` in screen pixels from the same geometry that is hit; it follows pan, zoom, rotation and scale. Fabric's own handles are hidden. The canvas therefore holds a temporarily un-cropped image: it is modelled as a session holding the scene from before it, which is what `getDoc` returns, and `commit` records nothing while it is open.
- Input while cropping: Fabric never sees a primary press (the capture-phase `mousedown` listener keeps it, as for the hand tool). A primary press on a handle drags that edge or corner (free aspect); inside the box moves it; anywhere else applies the crop and does nothing else. The rectangle stays inside the image, never flips, and keeps each side at least 8 scene units as displayed (`8 / scale` source pixels, at least one, capped by the image's side and by the side's length when the drag began). The pure geometry is in `src/model/crop.ts`; rotation is handled by converting the pointer to the image's source pixels. Wheel, zoom keys and buttons, Space-drag and the middle button pan and zoom as usual; the title stays editable.
- Ending: Enter (outside fields and buttons) or Done applies; Esc or Cancel restores the image exactly, with no history entry and no save. Applying a crop equal to the one the session began with records nothing and saves nothing. While the crop is open and its stored form differs from the one it began with, `EditorState.canUndo` is true (even with an empty history): Undo applies the crop, then undoes it; it returns to history's own value when the rectangle returns to the start (refreshed when a drag ends). Applying a changed crop is one history step; the image stays selected with its handles, and `left`/`top` move by the rotated, scaled offset of the crop's corner so the kept pixels do not move. Cropping back to the whole image removes `crop`.
- Keys while cropping: only Esc, Enter, the zoom keys and Space respond; every other shortcut is ignored, and kept from the browser (`preventDefault`, so Ctrl/Cmd+A does not select the page's text), as it is mid-gesture. Keys that are not shortcuts, and keys typed in a field, are left alone. When crop mode ends by any path, the canvas element's cursor is reset at once; when the board goes read-only it is set to the hand at once (`enterReadOnly`).
- Commands while cropping (tools, undo and redo, layer rows and padlocks, inspector buttons, Add image, an import or drop completing) apply the crop first, as its own history step if it changed anything, and then run. This lives in one place, `finishEditing`, which every command already calls; panning keeps crop mode open. A drag in flight ends with the rectangle as it is.
- Interruptions: a window blur during a handle drag returns that drag to where it began and leaves crop mode open; a blur with no drag changes nothing. The board going read-only cancels the crop (before the edit is left in `enterReadOnly`), committing and saving nothing. Only the primary button edits the crop; a lost primary release is healed from the next mouse event's `buttons` (the drag ends where it is). `dispose` removes a drag's listeners.
- Fit (`fitImage`) shows the whole original at the largest uniform scale at which it fits inside the image's current box (to stored precision: the scale is rounded to 5 decimals, so the result can exceed the box by a few hundredths of a unit; idempotence matters more), centred on it, same angle; the crop is removed and the box shrinks to the image's aspect ratio. Fill (`fillImage`) keeps the box (centre, displayed size, angle) to stored precision and covers it with the largest centred crop of the original that has the box's aspect ratio, at one uniform scale (`coverBox`): the crop's sides are rounded first and its position is centred from the rounded sides; the scale (5 decimals) is whichever of box width / crop width and box height / crop height keeps both sides closest. Stored precision means the centre within 0.01 and each side within 0.015 × scale + 0.000005 × that side in source pixels (pinned by a seeded sweep). Both Fit and Fill are idempotent: applied to their own result they change nothing, so straight after either its button is disabled. Both are for one unlocked image on an editable board that is not busy, apply an open crop first, and are one history step, or nothing at all when they would change nothing; the inspector disables a button that would change nothing (`SelectionInfo.image`). The maths is in `src/model/crop.ts` (slice 4, replace image, reuses `coverBox`).
- Replace image (P1): the inspector's "Replace image" button, for one unlocked image; disabled otherwise. One hidden file input serves Add image and Replace image (the input remembers the target in `data-replace-for` and takes a single file in that mode). Pressing the button leaves the current edit (an open crop is applied as its own step) and fixes the target by id (`replaceTarget()`, null when unavailable: before loading, read-only, busy, or not exactly one unlocked image). The target is never chosen when the file arrives: the file dialog can stay open while other things happen. Cancelling the dialog does nothing.
- Replace image, applying (`replaceImageFile(targetId, file)`): the file is read and decoded like an import. When that has finished: an unusable file gives a notice naming it and changes nothing; a disposed editor does nothing; a board that went read-only gives a notice and changes nothing; while a gesture is unsettled the replacement waits (`stagedReplacements`, applied by `idle()` in the order the replacements were requested, each as its own step; dropped with a notice if the board goes read-only), never inside a Fabric callback; otherwise it is applied at once. For one image the last pick wins: every `replaceImageFile` call gets a request number, and a replacement that arrives after a newer request for the same image has been applied is dropped silently (no notice, no history, nothing saved; undo does not reset this); an older one that arrives first is still applied as its own step and then replaced. Different images are independent. Applying leaves the current edit first (an open crop is applied as its own step, so on the same image the replacement works from the box after the crop), then finds the target by id: gone, no longer an image, or locked gives a notice and changes nothing further. A target that is not selected any more is still replaced and the selection is left as it is (a member of a multi-selection is taken out while it changes and the same selection is formed again).
- Replace image, result: same id, owner (not re-decided: the box does not move), stacking, angle and lock; the same box (centre and displayed size, to the stored precision of Fill); the new picture covers it like Fill (`replaceRecord`, built on `coverBox`), so a picture with the box's aspect ratio gets no `crop` key and only a new scale; the old crop is discarded; `assetId` is the new asset's. The same Fabric object is kept and given the new element (`setImageElement`). One history step; undo restores the old picture, crop, scale and position exactly, because the old picture stays decoded in the session's asset cache. Fit afterwards shows the whole new picture inside the box (the existing Fit rule).
- Replace image, assets: the new picture's bytes are stored by the first save whose document references them, in the same transaction (`writeBoard` in `boardStore.ts` stores any referenced asset that is not stored yet, from the session's cache, and refuses to write a document whose reference has no bytes). The old picture's bytes stay stored until a load prunes what the stored document does not reference, and stay in the session's memory, so an undo can bring the old picture back and the next save re-stores its bytes if another tab pruned them. A replacement that is abandoned (target gone or locked, read-only, disposed) leaves its picture decoded in memory but never referenced, so its bytes are never stored.
- Ownership: applying a crop and Fit change the image's box, so they count as resizing it: its owner is decided by `ownerAfterManipulation` with its current owner, its new centre and no co-transformed frames. Fill leaves the box alone and never changes ownership. None of them changes z-order, id or lock.

## Board appearance

- The backdrop is board metadata like the title. It is rendered behind the canvas and its pattern follows pan and zoom. Frames and content keep their own colors. Opening the Appearance panel finishes a canvas edit first. Appearance changes are editable-board commands, outside scene history, and go through autosave's normal revision check.
- Optional `appearance` rides on every wire version. No version or database upgrade. Missing or invalid settings fall back to the original background and dots, and valid named presets survive independently. Reset drops the custom style and keeps the presets. Omit the entire field when it has neither. Built-in presets are included in the app, and custom ones are local to the board.

## Storage and migration

- Everything is stored locally in IndexedDB database `yuriful`: one board row, and image bytes in a separate store. Document and bytes are written in one transaction.
- Every save re-checks a revision token inside its own transaction. A tab of this build whose view is stale never overwrites: it becomes read-only instead. A cleanup of unused image bytes from a stale view does nothing. A document is never written with an image reference that has no stored bytes.
- Text formatting (`font`, `align`, `color`, `spans`, `headings`) lives in optional fields of the text record in every stored version. A span can store marks and a font override different from the base. `parseDoc` reads formatting leniently into canonical form and stays strict about everything else. Default or undefined formatting keys are absent, so a plain text is stored exactly as before. Scene equality compares spans and headings structurally.
- A drawn text box stores its `minHeight` in scene units in every wire version. Zero represents a flat drag. Missing or invalid values keep the legacy behavior for existing boxes. There is no document or database version change.
- A text can also have a rich form (`src/model/textDoc.ts`): `blocks` (headings, paragraphs, lists, checklists, quotes, code blocks, dividers and the inline `code` mark), a fixed `height` and paper (`surface: 'card'`). This build makes and edits `blocks` and a fixed `height`; it cannot make paper yet. `blocks` is read strictly: an unknown block type, a malformed container, or more than 6 levels of nesting, 10,000 nodes or 500,000 characters in one text makes the document unreadable, never silently shortened. Marks, fonts, an ordered list's start, a checkbox's state, `height` and `surface` are read leniently. A text has one canonical form: blocks that hold only paragraphs and headings without `code` are stored in the compact form (`text`, `spans`, `headings`); otherwise `blocks` is the authority, `text` is its plain-text projection and there are no `spans` or `headings`. Scene equality compares blocks structurally. `serializeDoc` puts every text with a rich field through the same canonicalization before it chooses the wire version, so that text's content is written exactly as a load gives it back: blocks that collapse are written compact and need no version 3, `text` is their projection, and an invalid `height` or `surface` is not written. The rest of the record is written as the editor holds it, so what a load still cleans up (a dangling owner, or a caption whose image is missing) is written as it is and dropped when the board next loads. The store never writes a document that `parseDoc` would refuse (rich content that is malformed or over the bounds, or a document that cannot be prepared for writing at all). Before every save it runs `isLoadableDoc`, the same walk and strict checks as `parseDoc` without canonicalizing a compact text's formatting, which is lenient and cannot make a load fail. A refused save fails with `UnstorableBoardError` before anything is opened, upgraded or written, and the autosaver reports it like any other failed save, as "Couldn’t save" with Retry, never as saved and never retried on its own.
- Loading never rewrites the board row. After a complete restore it only removes image bytes the stored document does not reference; a load that ends read-only writes and removes nothing.
- A board saved by an earlier build must open by ordinary forward migration. A board without frames or rich text keeps the milestone 1 document shape; `parseDoc` accepts stored versions 1, 2 and 3 and rejects anything else, and a database newer than version 3 opens read-only.
- The first save of a board with a frame upgrades the database to version 2 in the same transaction that writes the board. The first save of a board with a rich text (any text with `blocks`, `height` or `surface`) is written as version 3, with `frames` always present, and upgrades the database to version 3 in the same transaction. Both are deliberately one-way: an older build can no longer open the board, and the database is never demoted when the frames or rich texts are later removed. An upgrade that another tab blocks fails after a few seconds as a retryable error that writes nothing; it does not make the board read-only.
- A board that uses a rich field this build cannot edit (`EDITABLE_RICH_FIELDS` holds `blocks` and `height`, so `surface`) opens read-only with the newer-build message, exactly like a newer database: nothing is shown, selected, edited, saved or pruned, so no save can drop the field.
- The existing board is early test data and the owner accepts one-way forward migration. Do not add backup, rollback, downgrade or old-build compatibility machinery unless asked.

## Out of scope for now

- Publishing, guest viewing, accounts, auth and any backend; mobile and touch input; frames inside frames; clipping content to a frame; rotating a frame; free-aspect or skew transforms of a group; adopting objects by drawing or moving a frame; cropping the stored image bytes; aspect-locked crops, crop presets, and rotating or zooming an image inside its crop; filters and masks.
