# Yuriful repository guidance

## The project

Yuriful is a desktop-first freeform reference canvas: you lay out images and text on an infinite, pannable, zoomable board and group finished spreads into named frames. It is local-only. There is no account, no server and no cloud storage; a board lives in the browser's IndexedDB.

- Explain changes through the experience of using the canvas. Use plain, direct language and concrete examples ("drag a frame over a loose image and it is left behind").
- Keep shipped behaviour, approved plans, open design questions and future ideas distinct. Avoid inflated claims and long inventories of changed files.
- [README.md](README.md) describes the app to the person using it. This file states how to work on it, and repeats the product rules only as constraints on changes.

## Questions before changes

- Questions such as "how could we do this?" or "is this possible?" are requests for discussion, not permission to edit. Explain the options, tradeoffs and proposed approach first, and wait for explicit permission to implement.
- Keep any investigation needed to answer the question read-only.

## Settled decisions and approved plans

- Milestone work follows a plan the owner approved. The plan's stated rules are the authority for user-facing behaviour.
- Do not redefine an agreed rule because a review found an awkward edge case. Keep the rule, pin it with a test, record the edge case under "Known limits" in the README as an open design question, and report it.
- Within the authorized implementation scope, fixing a crash, data loss, or behaviour that contradicts the plan needs no extra approval; report it. This does not turn a question, a request to review or a read-only investigation into permission to edit.
- A change to what a rule *is* needs the owner first. When unsure whether a change redefines a rule or only makes it work as stated, treat it as a redefinition: keep the plan's behaviour and report the alternative.
- The frame, transform and storage rules below are settled. Do not reopen them, and ask only about consequential unknowns.

## Skills

- This repository has no project skills yet (there is no `.agents/skills/` or `.claude/skills/`). If skills are added, check them before planning the relevant work and apply the ones that fit. Do not assume a skill from another project exists here.

## Check lifecycle behaviour while implementing

- For any change to gestures, selection, text editing, saving or loading, identify the failure cases while designing and testing it, not afterwards:
  - a gesture interrupted by Esc, by the window losing focus, by a reload, or by the board going read-only;
  - a second mouse button pressed or released mid-drag, and a release that never arrives;
  - the autosave debounce firing, or a save already in flight, during a gesture;
  - an image import that finishes decoding during a gesture;
  - another tab having written the board, or pruned its image bytes;
  - every way of leaving a text edit (Esc, clicking elsewhere, clicking another object, Shift-click, a toolbar or panel button), remembering that typing is saved as it happens while history is recorded when the edit ends;
  - undo and redo straight afterwards, and input before the stored board has finished loading.
- Exercise the cases that apply with focused tests before asking for review. Independent review is a second check, not the first time these cases are considered. Documentation-only changes do not need them.

## Delegation and independent review

- The main agent is the coordinator: it owns requirements, decisions, task boundaries, integration, final verification and the result reported to the owner. Delegate bounded, independent work when it improves progress or review quality; keep small or tightly dependent steps local.
- Use the delegation tools, roles and models actually available in the current session, and preserve the owner's model choices. Subagents report to the coordinator, do not delegate further, and do not mutate Git state. Use at most three at once.
- Before spawning, give each subagent its files, acceptance criteria and checks. Editing subagents share this checkout: they preserve others' edits and report overlap before writing. Reviewers do not edit the repository.
- After each committed slice, have an independent subagent review that commit against the plan and the neighbouring code before starting the next slice. Do not simulate a review or substitute a self-review. If no subagent capability is available, say so rather than claiming a review.
- Give the reviewer the actual commit, not a summary of it, and ask for bugs, regressions and test gaps with a concrete failure scenario for each. Ask for correctness, the plan's acceptance behaviour and real-browser evidence first. If you ask a reviewer to break the code on purpose to see whether a test notices, name the few breaks that matter rather than requesting a sweep.
- A reviewer that runs checks does so in its own copy, so that it depends on neither the working tree nor the owner's dev server: `git archive <commit> | tar -x -C <scratch dir>`, a junction or symlink from that copy's `node_modules` to the repository's, and a different `E2E_PORT`. TypeScript's build info (`tsBuildInfoFile`, set in this repository's tsconfig files) and Vite's cache (`cacheDir`, by default) live under `node_modules` and would be shared through that link. Neither has a command-line switch: edit the copy's `tsconfig.app.json`, `tsconfig.node.json` and `vite.config.ts` to point both inside the copy.
- Fix valid findings in a follow-up commit, rerun the affected checks, and have the fix re-reviewed. A fix commit made after a re-review needs its own re-review. A review cut short (for example by a usage limit) has not cleared anything: resume or replace it.
- Report reviewer identities, a finding-by-finding disposition (fixed in which commit, or dismissed and why), and the checks actually run. Delegation does not expand authorization.

## Commits and publishing

- Commit in logical slices. Every commit must be a safe checkpoint: the app works and whatever it stores is valid. Run the checks for the changed surface, inspect the full diff, then commit.
- Write commit messages around what changes for the person using the canvas, then why. Report the checks actually run; never invent impact, counts or verification.
- Do not push, merge, reset, switch branches, rewrite history or clean up destructively unless asked. Preserve uncommitted changes you did not make.
- Choose the base of new work deliberately. Until `main` contains the current app together with `AGENTS.md` and `CLAUDE.md`, do not base on it: new work must descend from `origin/feat/milestone-2-frames`, or from a newer owner-approved branch that descends from it. Once `main` does contain them, use the up-to-date base the owner approves instead; this is not a standing rule to branch from the feature branch.
- Before starting, confirm that both instruction files exist on the chosen base and on the new branch. If they are missing, the base is wrong: pick a base that has them rather than copying the files onto an older app they do not describe.
- For a pull request: a short specific title; open with what was wrong or missing and what changes for the user; then the checks run and any gaps. Writing a description does not authorize pushing, filing or merging.

## Project shape

- One npm package (ES modules, strict TypeScript): React 19 for the chrome, Fabric.js 7 for the canvas, Vite for dev and build, Vitest (jsdom) for unit tests, Playwright for real-browser tests. There is no backend and no `.env`.
- Fabric is pinned at 7.4.0 by the lockfile, and `FrameCanvas` overrides Fabric internals. Do not change dependencies unless a task genuinely requires it; say why if you do.
- `src/model/` is pure, with no Fabric or DOM dependency: document types and validation (`types.ts`, `doc.ts`), frame ownership rules, scale limits and hit geometry (`frames.ts`), the canonical form of text formatting, how heading levels carry across an edit, what the formatting controls do to a range, a caret or a whole box, and the typing-shortcut matcher (`richText.ts`), crop, Fit and Fill geometry (`crop.ts`), `history.ts`, `layers.ts`, `viewport.ts`, `id.ts`.
- Only `src/editor/` imports Fabric, and `src/editor/Editor.ts` is the only part the UI talks to: it owns the canvas, history, assets and autosave and exposes an immutable state snapshot. `FrameCanvas.ts` holds the frame hit-testing, Shift-click and marquee rules; `cropLayer.ts` draws crop mode's overlay from the same handle geometry that is hit; `frameLayer.ts` the one geometry used both to draw and to hit a frame's outline and label; `objects.ts` converts between records and Fabric objects, including a text's formatting and Fabric's per-character styles, and sets the lock flags; `fonts.ts` maps font ids to CSS font chains; `assets.ts` decodes images and keeps their original bytes for the session; `layerList.ts` derives the layer list.
- `src/persistence/` is the IndexedDB store (`boardStore.ts`), the save status machine (`autosave.ts`) and fail-closed loading (`hydrate.ts`). `src/input/shortcuts.ts` maps keys to actions; `resolveEditingShortcut` there is the only resolver for keys pressed while a text is edited, and `typedCharacter` the only judge of whether a key typed a character that can complete a typing shortcut. `src/ui/` is React chrome only (`LayerPanel.tsx` is the layer list).
- Test support: `src/editor/testing/` (a fake Fabric; a driver that replays by hand the event sequence of Fabric's mouse handlers, which is an imitation and not evidence of Fabric's behaviour; a fake store and assets), `src/persistence/testing/legacyStoreV1.ts` (a frozen copy of milestone 1's storage code; never modernize it), and `e2e/helpers.ts` (seeding and reading IndexedDB).
- Working files use LF. If Git on the machine has `core.autocrlf=true`, `git stash` and checkouts rewrite files with CRLF; tools that match text literally must tolerate that.

## Dev server and ports

- `npm run dev` serves the working tree, by default on port 5173. The owner often has one running: every saved file hot-reloads into their open tab, on their real board.
- Do not start, stop, restart or kill a dev server or preview you do not own. Identify the process that owns a port before touching it; never use a broad kill.
- `npm run test:e2e` starts its own dev server on `127.0.0.1:5199` (override with `E2E_PORT`) and reuses one already listening there. It needs a dev server rather than a build, because the tests load `legacyStoreV1.ts` from it. Tests run in isolated browser contexts and must never use the owner's board. Concurrent runs need different ports.
- IndexedDB is per origin: `http://localhost:5173` and `http://127.0.0.1:5173` hold different boards.

## Editor and gesture invariants

- A pointer gesture is settled (selection re-formed, scale folded, ownership decided, history recorded) in one microtask queued from Fabric's callback, after Fabric's own mouse-up handling has returned. Removing an object is deferred the same way. Four things do run inside callbacks: a moved frame's followers are placed during `object:moving`; leaving a text edit commits (and decides a new text's owner) in `text:editing:exited` and in the `object:modified` that Fabric fires straight after it; and `text:changed` rewrites the changed text's character styles to their canonical form before the typing save is scheduled: each line keeps the level it had before the change (`textAfterEdit` in `richText.ts`), marks come from the styles, and the wrap width goes back to the one from before the change, widened only as far as the canonical text needs (Fabric 7.4 fires it after it has changed the text, shifted the styles and placed the caret, and does nothing to the text afterwards; a drag fires it on its source text as well as on the text it is dropped into); and, in the same `text:changed` callback straight after that, a typing shortcut converts the text (see below), before the typing save is scheduled, so no save sees a marker typed but not converted.
- A save never sees an unfinished gesture or an open crop: while one exists, the saved scene is the one from before it. Title and viewport are always live.
- Esc, a window blur, or the board going read-only cancels an unfinished drag, resize, scale, rotation, frame draft or text draft and restores the board from before it, with no history entry and no save. A press that moves nothing leaves no trace.
- While a gesture is unsettled only Esc and the zoom keys respond; every editing command and shortcut is ignored (an image import waits and is added afterwards as its own undo step). Wheel panning and zooming keep working, and the title stays editable.
- Only the primary mouse button edits. Presses of other buttons never reach Fabric, and a non-primary release during a primary drag is kept from it; the middle button pans.
- Undo and redo restore whole scenes, including frames and ownership. A commit that changes nothing records nothing and saves nothing.
- After `dispose()` the autosaver never saves again: nothing is scheduled, a save already in flight finishes without rescheduling or reporting, and `Editor.getDoc` refuses to describe the board (its canvas is being cleared).

- The Text tool's drag is a draft gesture like the Frame tool's (`Gesture.draft` with `tool: 'text'`, drawn through `canvas.draft`). It starts on a primary press on empty canvas or a frame's interior with the Text tool chosen, the hand out of effect, the board editable and no gesture in progress. Release settles in the usual microtask. Staged image imports go first because adding one ends the edit and would discard a new blank text. `addTextAt`/`createObject` then takes the drag's smaller x and y, width and minimum height if it meets the click slop in screen pixels and is at least two font sizes wide in scene units (`MIN_TEXT_DRAG_EMS`). Clicks and smaller drags get the default box (ten font sizes wide) at the press point. A `mouse:up` without a press creates nothing.
- A drawn text's actual height is its text height or stored `minHeight`, whichever is taller. Text starts at the top. Drawn boxes wrap at spaces and split overlong tokens at grapheme boundaries. The widest individual grapheme may raise the usable minimum width. Click-created boxes and earlier records retain Fabric's word wrapping and longest-word minimum width. Side handles change width. Corner scaling also scales and folds the drawn minimum height along with width and font size.
- Nothing is editable or saved before the stored board has loaded. A board that cannot be fully restored, or that another tab has changed, is read-only: no selection, no edits, no writes, no pruning; pan and zoom still work.
- A blank text is never part of the scene: it is not saved, not in history, and is discarded when its edit ends, whatever formatting it has.
- A text's formatting on the canvas is always its canonical record: what a save stores is what the canvas shows. Fabric is the live source of truth while a text is edited.
- A heading is a property of a line. After a text change a line's level is carried over from the levels before the change and how the text changed, never derived from character sizes (a paste or a drop brings the source's complete styles, sizes included); the bold of a heading is never stored as a mark. `objects.ts` remembers each text's last canonical state (text, levels, wrap width, base size). `toRecord` reads formatting from the Fabric object alone while the text is unchanged since that state, and carries the levels from it when the text has changed but its styles have not been rewritten yet (Fabric triggers scene reads in the middle of a drop). Anything that writes a text's formatting or base size goes through `writeTextFormatting` or `setTextFontSize` (scale folding, `setFontSize`), which redraw headings at their ratio and refresh that state. A formatting command goes through `applyTextFormatting` only: read the canonical formatting, change it with a pure function of `richText.ts`, write it back with `writeTextFormatting`; never Fabric's `setSelectionStyles`. The write keeps the box's alignment edge where it is and never touches the text, the caret or the selected range.
- Formatting commands act on the one selected text, behind the `editable && !busy` guard. While editing, marks, font and heading act on the selected range (a line touched only by a range that ends at its start is not counted). Alignment and colour act on the whole box. The change is saved as it happens and is part of the one undo step recorded when the edit ends (`text:editing:exited` always commits, because Fabric fires no `object:modified` when only formatting changed). On a box outside editing, all commands act on the whole box as their own undo step, coalesced per kind and text like the font size. A whole-box font change sets the base font and clears the span font overrides. A whole-box heading applies to every line but an empty last one (`lastBoxLine` for both the panel and the command). Body text also clears an empty last line. A command that changes nothing records and saves nothing. A command on a blank text being typed into saves nothing and records no removal.
- Marks and a font chosen with only a caret are pending. The editor keeps them for that text, shows them as the next character's state and gives them to the characters inserted on `text:changed`. It drops them on `text:selection:changed` (caret moves other than typing or composition), when the edit ends and when records are applied. A heading line is always bold. `pendingMarksAt` drops only bold whenever the caret's line is or becomes a heading, after a heading command or text change. A Backspace revert of a shortcut restores all pre-shortcut pending formatting. Bold changes only the normal lines in a mixed range.
- Typing shortcuts (`# `, `## `, `### ` at the start of a line; a closing `**` or `*`) fire only for one character typed at the caret with nothing replaced: the change is the one diff the reconcile works out (`reconcileTextFormatting`'s `seen`), the character is the one `typedCharacter` saw on its keydown (cleared by the text change it causes and by any keyup), the text is the edited, active one, the board is editable, no gesture is unsettled and no IME composition is in progress. Pasted, dropped, composed and loaded markers stay literal. `matchTypingShortcut` reads only the caret's line; its literal cases are pinned by tests. The text and its formatting change in one step through `replaceEditedText` (which writes with `writeTextFormatting` and sets Fabric's `_text` by laying the text out, its grapheme selection directly, and its hidden textarea's value and selection through `_updateTextarea`): Fabric's next `onInput` diffs the textarea against the object, so the two must agree. After bold or italic fires, what is typed next is plain through a pending "off". Backspace straight afterwards (no modifier, from the edited textarea, not composing) restores the exact pre-conversion text, formatting, caret and pending marks; that offer is dropped by the next text change, any caret or selection move, any formatting command or font size change, the end of the edit and `applyRecords`. A conversion never changes ownership and is part of the edit's one undo step.
- Formatting controls are buttons that never take focus (`Overlays` and `Inspector` prevent the mousedown default), so using one keeps the edit, its caret, its range and typing. Ctrl/Cmd+B, I, U while editing are claimed only from the edited text's hidden textarea, never with Alt or Shift, never during composition, by the window keydown listener (Fabric 7.4 lets them bubble); a held key's auto-repeat is claimed (default prevented) and toggles nothing, also on a selected box; on a box not being edited only when exactly one text is selected. `resolveShortcut` still returns null while a text is edited, and nothing claims Esc or any key with Alt held in the edit.

## Frames (settled)

- A frame is a named, unrotated rectangle behind all content. It clips nothing. It is grabbed by its label or within 6 screen pixels either side of its outline; its interior is click-through. A label or outline wins over content lying on top of it.
- Ownership is stored on each object (`frameId`) and never recomputed from position. Loading restores it as stored (an owner that names no existing frame is dropped).
- **An object changes owner only through its own movement.** When content is moved, resized, rotated or created, it keeps its owner if that frame was transformed in the same gesture, or still contains its centre. Otherwise it joins the front-most frame that contains its centre and was not transformed in that gesture, or becomes loose. An owner is sticky: a frame in front that also contains the object does not take it.
- "Centre" is the centre of the object's box, including the wrapping width and actual height of text. The awkward case of a newly placed text whose box is much wider than its words remains an open design question in the README. A drawn minimum height contributes to the centre. The owner is decided again when the first edit ends, so text that grows below a frame may end up loose (see `e2e/texttool.spec.ts`).
- **Moving, resizing or drawing a frame never adopts anything.** A loose object that a frame was moved over or drawn round stays loose until the object itself is moved.
- Moving a frame together with loose objects leaves them loose. Things it already owns stay owned, with no containment test, when they are transformed together with it.
- Moving a frame carries its unselected members exactly once. A member that is itself selected moves through the selection only, never twice.
- A resized frame releases members it no longer contains; they become loose and are not handed to another frame. Deleting a frame keeps its contents, loose.
- A click without movement, selecting, reordering, renaming, typing in existing text, typing shortcuts in existing text, changing font size, formatting an existing text (marks, headings, font, alignment, colour, even when a heading makes the box taller and moves its centre out of its frame), undo, redo and loading never change ownership.
- Pressing the label of a frame that is part of the current multi-selection acts on the whole selection.

## Transforms (settled)

- **A frame resized alone changes its own shape freely and leaves its contents where they are.** It never stretches or moves them. Each side stops at 24 units (or at its own length if it was already shorter).
- Transforming contents with their frame is explicit: "Select with contents" selects a frame plus the unlocked things it owns, and that multi-selection is then moved or scaled as one.
- A multi-selection can be moved, scaled proportionally from a corner, and (if it contains no frame) rotated. There is no free-aspect stretch or skew of a group, and Shift does not unlock one. Every reachable canvas state must be representable in the stored records.
- One scale factor per proportional gesture: limits (text 6 to 400 px, a frame's smaller side at least 24 units) are computed from pre-gesture values and applied once to the whole selection, never per member, and an out-of-range member is never snapped into range. No transform is applied twice.

## Selection layout

- Align moves two or more unlocked selected items on one scene axis, using their displayed axis-aligned bounds. Left, top, right and bottom use the selection's outer edge. Center uses the midpoint of the selection's span. Distribute keeps the two outer items in place and spaces the gaps between three or more items. If there is insufficient room, that axis is disabled. Moves use the normal stored position precision.
- A moved frame carries its unselected members, including locked ones. A selected member takes only its own layout displacement. Apply the ordinary ownership rules to moved items and leave stationary items alone. One changed layout is one history step. Shape, angle, z-order and selection are preserved.

## Duplication

- Duplicate is inert before load, on a read-only board, during a canvas gesture and for a locked selection. A valid command finishes an edit before it snapshots the scene. Each copy has a fresh id and starts unlocked. Source image bytes are shared. One command, including a frame with its owned items, is one history step.
- Copy explicitly selected objects and the owned contents of selected frames exactly once, preserving relative stacking within each band and bringing the copies to its front. Remap ownership to matching copied frames; other content copies use the ordinary placement rule against existing frames. Select the counterparts of the items explicitly selected.

## Layers (settled)

- The layer list (`EditorState.layers`) is derived from the canvas and never stored. It is flat and front-most first: all content front to back, then all frames front to back. Content is never grouped under its frame, because stacking order is global and independent of ownership; an owned item only names its owner, taken from stored ownership.
- A blank text is not listed, including one emptied while it is being edited. A text's label follows typing: `text:changed` refreshes the derived state, which marks nothing dirty and records nothing.
- A plain press goes to the front-most object under the pointer, except inside a multi-selection's box, where it goes to the selection (Alt or not). A locked object is never the target of a press (see Locking). With Alt held (`altSelectionKey`), a press goes to the selected object if it is under the pointer, even beneath other content, so that a covered object selected from the list can be dragged. It is an ordinary gesture (same settle path, ownership rules, one history step; Esc, also with Alt still held, and a window blur cancel it). Alt never changes frame hit rules: a frame's label or outline still wins over the selected object (`FrameCanvas.findTarget`), and a frame's interior stays click-through.
- Selecting from the list (`selectLayer`) changes nothing on the board: no history entry, no save, no ownership change. It ends a text edit first, like every other command, so typed text is committed as its own step. It is inert before the board has loaded, on a read-only board and while a gesture is unsettled.
- Reordering stays what `[`/`]` and `Ctrl/Cmd+[`/`]` already do: each kind moves within its own band, so frames stay behind content, and ownership never changes.
- Dragging in the list moves one unlocked row within its own band, including past a locked row. The upper and lower halves of a target row insert before and after it in the front-most-first list. Only a valid primary release at the previewed insertion changes the stack. The selection and ownership stay as they are. A changed drop finishes any text or crop edit first and records one reorder step. Esc, blur, a lost release, a read-only board or release without a valid insertion cancels the drag without committing a reorder.
- Rows must not take focus on a mouse press, or Space-to-pan and the letter shortcuts would act on the list. A row press first blurs a focused chrome field (font size, frame name, title), so that its keys do not act on the new selection; Fabric's hidden textarea is left to `selectLayer`, which ends a text edit itself. The same holds for a row's padlock button, which also never selects its row.

## Locking (settled)

- Storage: `locked?: true` is optional on every content record and on a frame record. Absent means unlocked; `locked: false` or an explicit `undefined` is never stored. There is no version bump and no database upgrade: wire versions 1 and 2 both read and write it, and a frameless board with a lock is still written as version 1. `parseDoc` keeps it only when it is exactly `true` (anything else is dropped, not fatal). A lock change is a scene change, so it is a history step and is saved.
- A locked object or frame is never the target of a press: Fabric's `evented` and `selectable` are off, so a press, a hover, an Alt-press or a double-click falls through to whatever is beneath it (or to the empty board, where it starts a marquee or, with the Text tool, places a text). A marquee, Select all and Shift-click never take it; a locked frame's label and outline are not grabbable and its label does not start a rename. Its handles are hidden, its movement, scaling and rotation are locked and a locked text is not editable, as defence in depth. These flags are set in one function in `objects.ts`, used by creation, lock and unlock, so that unlocking restores exactly what creation set.
- A locked item is selected only from the layer list, and only alone: **a selection that contains a locked item contains nothing else.** A toggle click on a locked row acts as a plain click; a toggle click on an unlocked row while a locked item is selected replaces the selection; Shift-click on the canvas never adds to a locked selection (`FrameCanvas.handleMultiSelection`). `selectByIds` enforces the rule centrally for every selection the editor forms, including the one restored by id after undo and redo: locked items are dropped from a restored multi-selection, and a restored single locked selection is kept.
- While a locked item is selected nothing edits it: no move, resize or rotation, and delete, the four layer-order commands, font size, rename, "Select with contents" and text editing do nothing. `SelectionInfo.locked` is true exactly when the selection is one locked item, and every `layer` flag is then false.
- Commands: `setSelectionLocked` (the inspector button), `toggleLayerLock` (a row's padlock, whether or not the row is selected) and `Ctrl/Cmd+Shift+L` (unlock a single locked selection, otherwise lock the selection). Each is inert before the board has loaded, on a read-only board and while a gesture is unsettled, and ends a text edit first (typed text is its own step; a blank text is discarded). One history step when something changes, none when nothing does. Locking a multi-selection clears it; locking the single selection keeps it selected; a padlock that locks a member of a multi-selection takes just that member out; unlocking never changes the selection. Locking and unlocking never change position, size, stacking or ownership.
- A lock guards direct manipulation only. Frame relations keep their settled rules: a locked member keeps its owner and follows its frame's move as an unselected member, exactly once; "Select with contents" selects a frame plus its unlocked members (so a locked member follows a move and is not scaled); a frame whose size changed releases members it no longer contains, locked or not; deleting a frame leaves its locked members, loose; content moved into or out of a locked frame joins or leaves it by its own movement. A locked frame cannot be moved, resized, renamed, reordered or deleted.
- New things are never locked. The Frame tool draws over anything, as before; zoom-to-fit includes locked things; on a read-only board the padlocks are shown and inert.

## Image tools (settled)

- Storage: `ImageRecord.crop?: { x, y, width, height }` is the visible rectangle of the ORIGINAL image in source pixels (x/y from its top-left); absent means the whole image. Cropping is non-destructive: the stored bytes are never changed. With a crop, `left`/`top` are the top-left of the displayed (cropped) box, the displayed size is `crop.width * scaleX` by `crop.height * scaleY`, and `angle` turns that box as for any image. "Centre" for ownership is the centre of the displayed box.
- No version bump and no database upgrade: wire versions 1 and 2 both read and write `crop`. `parseDoc` keeps it only when it is an object of finite numbers with `x >= 0`, `y >= 0`, `width > 0`, `height > 0` (anything else is dropped and the image shown whole, not fatal). `serializeDoc` writes a fresh copy only when present; an undefined key is never stored, and a crop equal to the whole image is never stored (`toRecord` omits it). There is ONE stored-crop decision, `storedCrop` in `src/model/crop.ts`, used by the geometry (`coverBox`, so Fill and replace; `clampCrop`; closing crop mode) and by the Fabric conversion (`createObject`, `imageCropOf`/`toRecord`), and so by everything saved: the crop's EDGES are clamped to the image and rounded to 0.01 source pixels, its sides are taken from the rounded edges (so a stored crop never reaches outside the image and clamping it again changes nothing), and it is the whole image exactly when its rounded edges are the image's edges (no tolerance beyond the rounding: a crop that differs from the whole image at stored precision is never dropped). What Fill, Fit and replace compute is exactly what `createObject` then `toRecord` give back (pinned by seeded sweeps). The one value that is not on the 0.01 grid: a crop thinner than the stored step on an axis (under 0.01 source pixels, which only an absurd box shape produces) keeps its true positive side rather than collapsing to zero.
- `sceneEqual` compares nested record values structurally (plain objects and arrays by content; NaN equals NaN; absent equals `undefined`), so two snapshots of the same cropped image are equal and a changed crop is a change. `toRecord` reads the crop from the Fabric image (`cropX`, `cropY`, `width`, `height` against its natural size) and emits a fresh object every time. A stored crop that reaches outside the decoded image is clamped to it when the object is created (`clampCrop`, which is `storedCrop`, in `createObject`); if nothing is left the image is shown whole. A crop this build writes is never changed by that.
- Crop mode (`startCrop`): only for one unlocked image, on an editable board, while no gesture is unsettled; inert otherwise. Entry points are the inspector's "Crop image" button and a double-click on an unlocked image with the Select tool (deferred by a microtask, like the frame-label double-click; not when the double-click began with the press that applied a crop). Starting it switches any other tool to Select. `EditorState.cropping` says it is open.
- While cropping, the whole original is shown in place (the kept pixels do not move), the part outside the crop rectangle is dimmed, and a box with eight handles is drawn in `after:render` in screen pixels from the same geometry that is hit; it follows pan, zoom, rotation and scale. Fabric's own handles are hidden. The canvas therefore holds a temporarily un-cropped image: it is modelled as a session holding the scene from before it, which is what `getDoc` returns, and `commit` records nothing while it is open.
- Input while cropping: Fabric never sees a primary press (the capture-phase `mousedown` listener keeps it, as for the hand tool). A primary press on a handle drags that edge or corner (free aspect); inside the box moves it; anywhere else applies the crop and does nothing else. The rectangle stays inside the image, never flips, and keeps each side at least 8 scene units as displayed (`8 / scale` source pixels, at least one, capped by the image's side and by the side's length when the drag began). The pure geometry is in `src/model/crop.ts`; rotation is handled by converting the pointer to the image's source pixels. Wheel, zoom keys and buttons, Space-drag and the middle button pan and zoom as usual; the title stays editable.
- Ending: Enter (outside fields and buttons) or Done applies; Esc or Cancel restores the image exactly, with no history entry and no save. Applying a crop equal to the one the session began with records nothing and saves nothing. While the crop is open and its stored form differs from the one it began with, `EditorState.canUndo` is true (even with an empty history): Undo applies the crop, then undoes it; it returns to history's own value when the rectangle returns to the start (refreshed when a drag ends). Applying a changed crop is one history step; the image stays selected with its handles, and `left`/`top` move by the rotated, scaled offset of the crop's corner so the kept pixels do not move. Cropping back to the whole image removes `crop`.
- Keys while cropping: only Esc, Enter, the zoom keys and Space respond; every other shortcut is ignored, and kept from the browser (`preventDefault`, so Ctrl/Cmd+A does not select the page's text), as it is mid-gesture. Keys that are not shortcuts, and keys typed in a field, are left alone. When crop mode ends by any path, the canvas element's cursor is reset at once; when the board goes read-only it is set to the hand at once (`enterReadOnly`).
- Commands while cropping (tools, undo and redo, layer rows and padlocks, inspector buttons, Add image, an import or drop completing) apply the crop first, as its own history step if it changed anything, and then run. This lives in one place, `finishEditing`, which every command already calls; panning keeps crop mode open. A drag in flight ends with the rectangle as it is.
- Interruptions: a window blur during a handle drag returns that drag to where it began and leaves crop mode open; a blur with no drag changes nothing. The board going read-only cancels the crop (before the edit is left in `enterReadOnly`), committing and saving nothing. Only the primary button edits the crop; a lost primary release is healed from the next mouse event's `buttons` (the drag ends where it is). `dispose` removes a drag's listeners.
- Fit (`fitImage`) shows the whole original at the largest uniform scale at which it fits inside the image's current box (to stored precision: the scale is rounded to 5 decimals, so the result can exceed the box by a few hundredths of a unit; idempotence matters more), centred on it, same angle; the crop is removed and the box shrinks to the image's aspect ratio. Fill (`fillImage`) keeps the box (centre, displayed size, angle) to stored precision and covers it with the largest centred crop of the original that has the box's aspect ratio, at one uniform scale (`coverBox`): the crop's sides are rounded first and its position is centred from the rounded sides; the scale (5 decimals) is whichever of box width / crop width and box height / crop height keeps both sides closest. Stored precision means the centre within 0.01 and each side within 0.015 × scale + 0.000005 × that side in source pixels (pinned by a seeded sweep). Both Fit and Fill are idempotent: applied to their own result they change nothing, so straight after either its button is disabled. Both are for one unlocked image on an editable board that is not busy, apply an open crop first, and are one history step, or nothing at all when they would change nothing; the inspector disables a button that would change nothing (`SelectionInfo.image`). The maths is in `src/model/crop.ts` (slice 4, replace image, reuses `coverBox`).
- Replace image (P1): the inspector's "Replace image" button, for one unlocked image; disabled otherwise. One hidden file input serves Add image and Replace image (the input remembers the target in `data-replace-for` and takes a single file in that mode). Pressing the button leaves the current edit (an open crop is applied as its own step) and fixes the target by id (`replaceTarget()`, null when unavailable: before loading, read-only, busy, or not exactly one unlocked image). The target is never chosen when the file arrives: the file dialog can stay open while other things happen. Cancelling the dialog does nothing.
- Replace image, applying (`replaceImageFile(targetId, file)`): the file is read and decoded like an import. When that has finished: an unusable file gives a notice naming it and changes nothing; a disposed editor does nothing; a board that went read-only gives a notice and changes nothing; while a gesture is unsettled the replacement waits (`stagedReplacements`, applied by `idle()` in the order the replacements were requested, each as its own step; dropped with a notice if the board goes read-only), never inside a Fabric callback; otherwise it is applied at once. For one image the last pick wins: every `replaceImageFile` call gets a request number, and a replacement that arrives after a newer request for the same image has been applied is dropped silently (no notice, no history, nothing saved; undo does not reset this); an older one that arrives first is still applied as its own step and then replaced. Different images are independent. Applying leaves the current edit first (an open crop is applied as its own step, so on the same image the replacement works from the box after the crop), then finds the target by id: gone, no longer an image, or locked gives a notice and changes nothing further. A target that is not selected any more is still replaced and the selection is left as it is (a member of a multi-selection is taken out while it changes and the same selection is formed again).
- Replace image, result: same id, owner (not re-decided: the box does not move), stacking, angle and lock; the same box (centre and displayed size, to the stored precision of Fill); the new picture covers it like Fill (`replaceRecord`, built on `coverBox`), so a picture with the box's aspect ratio gets no `crop` key and only a new scale; the old crop is discarded; `assetId` is the new asset's. The same Fabric object is kept and given the new element (`setImageElement`). One history step; undo restores the old picture, crop, scale and position exactly, because the old picture stays decoded in the session's asset cache. Fit afterwards shows the whole new picture inside the box (the existing Fit rule).
- Replace image, assets: the new picture's bytes are stored by the first save whose document references them, in the same transaction (`writeBoard` in `boardStore.ts` stores any referenced asset that is not stored yet, from the session's cache, and refuses to write a document whose reference has no bytes). The old picture's bytes stay stored until a load prunes what the stored document does not reference, and stay in the session's memory, so an undo can bring the old picture back and the next save re-stores its bytes if another tab pruned them. A replacement that is abandoned (target gone or locked, read-only, disposed) leaves its picture decoded in memory but never referenced, so its bytes are never stored.
- Ownership: applying a crop and Fit change the image's box, so they count as resizing it: its owner is decided by `ownerAfterManipulation` with its current owner, its new centre and no co-transformed frames. Fill leaves the box alone and never changes ownership. None of them changes z-order, id or lock.

## Board appearance

- The backdrop is board metadata like the title. It is rendered behind the canvas and its pattern follows pan and zoom. Frames and content keep their own colors. Opening the Appearance panel finishes a canvas edit first. Appearance changes are editable-board commands, outside scene history, and go through autosave's normal revision check.
- Optional `appearance` rides on both wire versions. No version or database upgrade. Missing or invalid settings fall back to the original background and dots, and valid named presets survive independently. Reset drops the custom style and keeps the presets. Omit the entire field when it has neither. Built-in presets are included in the app, and custom ones are local to the board.

## Storage and migration

- Everything is stored locally in IndexedDB database `yuriful`: one board row, and image bytes in a separate store. Document and bytes are written in one transaction.
- Every save re-checks a revision token inside its own transaction. A tab of this build whose view is stale never overwrites: it becomes read-only instead. A cleanup of unused image bytes from a stale view does nothing. A document is never written with an image reference that has no stored bytes.
- Text formatting (`font`, `align`, `color`, `spans`, `headings`) lives in optional fields of the text record in both stored versions. A span can store marks and a font override different from the base. `parseDoc` reads formatting leniently into canonical form and stays strict about everything else. Default or undefined formatting keys are absent, so a plain text is stored exactly as before. Scene equality compares spans and headings structurally.
- A drawn text box stores its `minHeight` in scene units in both wire versions. Zero represents a flat drag. Missing or invalid values keep the legacy behavior for existing boxes. There is no document or database version change.
- Loading never rewrites the board row. After a complete restore it only removes image bytes the stored document does not reference; a load that ends read-only writes and removes nothing.
- A board saved by an earlier build must open by ordinary forward migration. A board without frames keeps the milestone 1 document shape; `parseDoc` accepts stored versions 1 and 2 and rejects anything else, and a database newer than version 2 opens read-only.
- The first save of a board with a frame upgrades the database to version 2 in the same transaction that writes the board. This is deliberately one-way: the older build can no longer open it.
- The existing board is early test data and the owner accepts one-way forward migration. Do not add backup, rollback, downgrade or old-build compatibility machinery unless asked.

## Out of scope for now

## Code review rules

- Flag: settling a gesture, or removing an object, inside a Fabric callback; a frame gaining a member by being moved, resized or drawn; an owner lost to a frame that merely overlaps it; a member moved twice; contents stretched or moved by a lone frame resize; a per-member limit inside a proportional scale or in serialization; a canvas state the records cannot store; a heading level read from character sizes after a text change; a formatting write that bypasses `applyTextFormatting`/`writeTextFormatting` or uses `setSelectionStyles`; a formatting control that takes focus from, or ends, a text edit, or loses its selected range; a key claimed in a text edit with Alt or Shift held, during composition, or not from the edited text; a typing shortcut that fires on pasted, dropped or composed text, or that changes the object without its hidden textarea; Backspace claimed outside the moment straight after a shortcut fired; bold stored inside a heading line; a pending mark that outlives a caret move or the edit; a save that can see a half-finished gesture; a click or a read-only board that writes; selecting from the layer list that records history or saves; a selection that contains a locked item and anything else; a command or gesture that edits a locked item; a locked item reachable by a press, a marquee, Select all or Shift-click; `locked: false` or an explicit `undefined` written to storage; a lock change that is not a history step; a save that can see an open crop; a command that runs against the temporarily un-cropped image; a crop applied with movement of the kept pixels; a `crop` object shared between snapshots; a flat comparison of nested record values; a Fit or Fill that is not idempotent; a save scheduled or run after dispose; a crop rounded so that it reaches outside the image; two different whole-image decisions; a replacement applied to a target chosen when the file arrives rather than when the button was pressed; a replacement that moves or resizes the box, or re-decides ownership; a document written with a new asset before (or without) its bytes; a load that rewrites the board row; a save without the revision check; a test that reaches the owner's board or a live dev server; a test that cannot fail.
- Safe paths: deferred settlement; ownership decided by the pure rules in `src/model/frames.ts`; one scale factor per gesture; records as the source of truth; token-checked transactional writes; isolated browser contexts with seeded storage.
- Traps that have already cost time here:
  - The fake's multi-selection holds its members' absolute results, so it cannot detect a double move or wrong group geometry. Cover those in `e2e/`.
  - Removing an object inside Fabric's `text:editing:exited` makes Fabric throw afterwards. Defer the removal.
  - Objects cannot be flipped, so a handle dragged past its anchor stops at the last accepted scale. A test cannot reach a minimum size by dragging through the anchor; drag to just short of it.
  - Button names overlap ("Select" and "Select with contents", "Frame" and "Delete frame", "Lock" in the inspector and on every layer row, "Lock" and "Unlock", "Heading 1" and the like): use exact role locators in Playwright.
  - In Fabric 7.4, Ctrl+End in a text goes to the end of the line, not of the text, and End with a selection only collapses it: a test that wants the end of the text uses Ctrl+A then ArrowRight.
  - Fabric fires `text:selection:changed` before it stores the new selection in some paths (`IText.mjs` `_updateAndFire`): read the selection in a microtask, not in the handler.
  - The editor unit tests fake only `setTimeout`; `fake-indexeddb` runs on `setImmediate`, so real store writes need real macrotasks to finish.
